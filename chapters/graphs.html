Chapter 02

이중 그래프

ARTEX 는 "대상이 무엇인가"와 "어디까지 확인했는가"를 서로 다른 두 그래프에 나눠 담고, 둘을 앵커 테이블로 묶습니다. 이 분리 덕분에 병렬로 일하는 에이전트가 서로의 기록을 덮어쓰지 않고, 매번 새로 깨어나는 계획 에이전트가 PostgreSQL 만 읽고도 현황을 복원할 수 있습니다.

  • 탐색 그래프의 노드 7종, 상태 집합, 간선 5종을 스키마 제약과 함께 설명한다
  • 자산 그래프가 작업을 가로질러 공유되는 이유를 말하고, 프로그램이 계산하는 것과 에이전트가 제출하는 것을 구분한다
  • 앵커가 만드는 양방향 조회와 커버리지 정의를 식으로 쓰고 계산한다

왜 그래프가 둘인가

하나의 그래프에 모두 담으면 수명과 소유권이 서로 다른 데이터가 뒤섞입니다. 도메인, IP, 서비스 같은 자산은 작업이 끝나도 남고 여러 작업이 함께 참조하지만, "어떤 방향을 시도했고 무엇이 나왔는가"는 한 작업의 사고 기록입니다.

구분자산 그래프탐색 그래프
질문대상에 무엇이 있는가무엇을 시도했고 무엇이 나왔는가
범위작업을 가로질러 전역 공유작업마다 독립 (tasks.exploration_id 가 UNIQUE)
수명작업이 끝나도 유지작업과 함께 보관·아카이브
키 계산부모·자식 관계와 중복 제거 키는 프로그램이 계산노드 종류와 상태 전이는 스키마 제약과 서버 코드가 강제
에이전트의 역할원본 정보를 제출한다사실, 방향, 결과를 기록한다
설계 원칙: 에이전트는 사실만 내고 키는 프로그램이 만든다

자산 사이의 부모·자식 관계와 중복 제거 키를 모델에게 맡기면 같은 호스트가 표기 차이로 여러 노드가 되거나 관계가 어긋납니다. ARTEX 는 에이전트가 원본 속성만 제출하게 하고, 정규화와 연결은 코드가 합니다. LLM 이 만든 값을 그대로 키로 쓰지 않는다는 점은 에이전트 시스템 전반에 적용되는 방어적 설계입니다.

탐색 그래프: 노드, 상태, 간선

노드 종류는 exploration_nodes.kind 의 CHECK 제약으로 닫혀 있고, 종류마다 허용되는 상태 집합도 제약으로 고정됩니다. 잘못된 상태를 쓰려는 코드는 DB 가 거부합니다.

종류의미허용 상태
goal작업의 최종 목표open · met · abandoned
intent탐색 방향 하나. 계획 에이전트가 만들고 실행 에이전트가 맡는다open · running · paused · done · blocked · exhausted · stopped · deleted
fact실행 결과와 결론(음성 결과 포함). 작업 시작 시 뿌리 노드(origin)가 하나 만들어진다confirmed · dismissed · origin
finding확인된 취약점 기록. fact 와 구분된다confirmed · dismissed
hint사람이 주입한 힌트active · consumed
digest오래된 노드를 접어 둔 요약. 구성원은 지워지지 않는다active · superseded
begin예전 방식의 작업 뿌리. 새 작업은 쓰지 않는다 (DEPRECATED)open

간선은 exploration_edges.rel 로 다섯 가지 관계를 표현합니다. 모든 간선의 방향은 부모(상류) → 자식(하류) 로 통일되어 있어, 상류를 따라 올라가면 "이 결과가 어디서 왔는가", 하류를 따라 내려가면 "이 방향이 무엇을 낳았는가"를 알 수 있습니다.

관계방향뜻
spawns상위 → 의도목표나 이전 결과가 새 의도를 낳았다
yields의도 → fact의도를 수행해 결과가 나왔다
derived_fromfact → 의도이 결과를 근거로 다음 의도가 정해졌다
proves의도 → finding의도의 결과로 취약점이 입증되었다
coversdigest → 구성원요약 노드가 어떤 노드를 접었는지. "누가 X 를 접었는가"의 단일 출처
왜 뿌리 fact 가 필요한가

예전에는 작업 뿌리를 begin 노드로 따로 두었습니다. 지금은 작업을 만들 때 상태가 origin 인 fact 를 하나 심고, 모든 의도가 거기까지 거슬러 올라가게 합니다. "의도는 반드시 어떤 fact 와 연결된다"는 규칙이 첫 번째 의도부터 예외 없이 성립하므로, 혈통을 따라가는 조회 코드에 분기가 필요 없습니다.

자산 그래프: 전역 공유 진실 저장소

자산은 assets.type 이 여섯 종류(root_domain · subdomain · ip · service · app · endpoint)로 제한됩니다. 한 행에 도메인, IP, 포트, 열린 포트 목록, URL, 앱 정보 같은 속성이 함께 들어가며, 소속 회사(company_id)와 어떤 작업들이 이 자산을 다뤘는지(task_ids, 배열)를 기록합니다.

설계 결정이유
작업에 속하지 않고 전역 공유같은 대상을 여러 작업이 다뤄도 자산 행은 하나다. 작업이 끝나도 지식이 남는다
company_source 가 explicit / scope사람이 지정한 소속과 범위 규칙에서 파생된 소속을 구분한다. 범위를 다시 계산해도 사람이 한 지정은 지워지지 않는다
서비스와 엔드포인트의 부모 관계를 프로그램이 계산모델이 부모를 잘못 지정해 그래프가 끊어지는 일을 막는다
DNS·HTTP 보강은 에이전트와 무관한 워커 풀이 수행도메인 해석과 웹 확인 같은 결정적 작업은 LLM 호출 없이 비동기로 채운다

앵커: 두 그래프를 묶는 테이블 하나

두 그래프는 exploration_anchors(node_id, asset_id) 로만 연결됩니다. 기본 키가 두 열의 쌍이라 같은 연결은 한 번만 존재하고, 양쪽 모두 ON DELETE CASCADE 라서 노드나 자산이 지워지면 연결도 함께 사라집니다. asset_id 에도 색인이 있어 역방향 조회가 느려지지 않습니다.

방향질문쓰임
노드 → 자산이 의도와 결과는 어떤 자산을 겨냥했나실행 에이전트가 시작할 때 의도에 걸린 자산의 원본 정보를 가져온다
자산 → 노드이 자산은 이번 작업에서 어떤 의도로 다뤄졌고 무엇이 나왔나자산 화면의 탐색 이력, 커버리지 계산

실행 에이전트가 의도에 걸린 자산을 시작 정보로 받는다는 점이 중요합니다. 모델이 대화 기록에서 대상을 기억해 내는 것이 아니라, 앵커로 DB 에서 다시 읽어 옵니다. 세션이 바뀌어도 대상이 흔들리지 않습니다.

커버리지: 어디까지 확인했는가를 숫자로

작업은 task_scope 로 테스트 범위를 정합니다. 범위 항목의 kind 는 company · root_domain · subdomain · ip · cidr · icp · keyword 일곱 가지이고, source 는 auto(자산을 등록할 때 보수적으로 자동 추가), agent(에이전트가 도구로 추가), manual(사람) 입니다. 같은 범위는 유일 색인으로 한 번만 저장되어, 자동 추가를 다시 실행해도 결과가 같습니다.

$$\text{coverage} = \frac{|A \cap S|}{|S|}$$
여기서 \(S\) 는 활성 범위 항목에 매칭되는 자산 집합(분모), \(A\) 는 fact 노드에 앵커된 자산 집합(분자)이다. 의도나 finding 만 앵커된 자산은 분자에 들지 않는다.

분자를 fact 로 한정한 이유는 "그 방향을 시도했다"와 "결과를 얻었다"를 구분하기 위해서입니다. 시도만 하고 결과가 없으면 아직 확인한 것이 아니므로 계획 에이전트는 그 자산을 미테스트 백로그로 계속 봅니다.

취약점은 탐색 그래프의 finding 노드(예전 방식 핸들)와 별도 테이블 findings 의 레코드(독립 id)로 두 번 존재합니다. 후속 도구가 어느 id 를 받는지가 도구마다 다르므로, 보고서나 증거 연결 같은 단계는 반드시 해당 도구가 요구하는 id 종류를 구분해서 넘겨야 합니다. 이런 이중 id 구조는 마이그레이션 과정의 흔적이면서 실수하기 쉬운 지점입니다.

핵심 정리

  1. 자산 그래프는 전역 공유 진실 저장소, 탐색 그래프는 작업별 사고 기록이다. 수명과 소유가 달라 분리한다.
  2. 탐색 노드는 7종, 상태 집합은 DB 제약으로 닫혀 있고 간선은 부모에서 자식 방향의 5종이다.
  3. 에이전트는 사실을 제출하고 키와 관계는 프로그램이 계산한다.
  4. 앵커 하나로 노드→자산, 자산→노드 양방향 조회가 가능하고, 실행 에이전트는 앵커로 대상을 DB 에서 다시 읽는다.
  5. 커버리지는 범위에 매칭되는 자산 중 fact 에 앵커된 비율이다. 시도와 결과를 구분한다.

확인 퀴즈

탐색 그래프의 간선 방향 규칙으로 옳은 것은?

요약(digest)의 covers 도 요약에서 구성원 방향입니다. 방향이 통일되어 있어 상류·하류 탐색 코드가 관계마다 갈라지지 않습니다.

커버리지 분자에 들어가는 자산은?

시도(의도)와 결과(fact)를 구분합니다. 범위 밖 자산은 분자에도 분모에도 들지 않습니다.

자산 사이의 부모·자식 관계를 에이전트가 아니라 프로그램이 계산하는 이유로 가장 알맞은 것은?

모델 출력을 키로 직접 쓰지 않는 것은 에이전트 시스템의 기본적인 방어 설계입니다.
